# HTB Delivery

**Target:** `10.129.8.154`  
**Operating System:** Linux (Debian)  
**Difficulty:** Easy  
**Attack Path:** osTicket Email Disclosure → Mattermost Account Access → SSH → Password Hash Cracking → Root

## 1. Enumeration

I started with an Nmap scan to identify the target's exposed services and determine which applications might provide an initial foothold.

```
nmap -sC -sV -p- --min-rate 1000 10.129.8.154 -oN nmap.txt
```

The relevant results were:

|Port|Service|Details|
|---|---|---|
|22|SSH|OpenSSH 7.9p1|
|80|HTTP|nginx 1.14.2|
|8065|HTTP|Mattermost 5.30.0|

The web services exposed two interesting applications:

- `http://helpdesk.delivery.htb` — osTicket
    
- `http://delivery.htb:8065` — Mattermost
    

I added the hostnames to my local `/etc/hosts` file.

```
echo "10.129.8.154 delivery.htb helpdesk.delivery.htb" | sudo tee -a /etc/hosts
```

### 1.1 osTicket

The helpdesk application allowed visitors to create support tickets without an existing account. After submitting a ticket, osTicket provided a ticket ID and an associated email address in the format:

![OSTicket 1](/assets/images/delivery_osticket_1.png)

```
<ticket_id>@delivery.htb
```

I also received the information needed to check the ticket's status and view its conversation thread.

### 1.2 Mattermost

Mattermost was accessible on port 8065. I attempted to register a new account, but the application required email verification. Since Mattermost accepted addresses ending in `delivery.htb`, I needed a way to receive a verification link sent to that domain.

Rather than abandoning the registration process, I investigated whether the helpdesk application could be used to retrieve the verification email.

## 2. Exploiting the Email Workflow

OsTicket assigned a delivery.htb email address to newly created tickets, and its ticket thread displayed messages associated with the ticket.

I used this workflow to obtain a Mattermost account.

1. Created a new support ticket through osTicket.
    
2. Recorded the ticket ID and the email address assigned to it.
    
3. Opened the ticket thread using the ticket ID and the email address originally supplied when creating the ticket.
    
4. Started a Mattermost registration using the ticket-associated email address.
    
5. Mattermost sent an account-verification link to that address.

![OSTicket 1](/assets/images/delivery_osticket_2.png)

6. Returned to the osTicket ticket thread and retrieved the verification link.
    
7. Opened the link to verify the Mattermost account and logged in.
    

This worked because the helpdesk workflow exposed the verification message through the ticket thread. The email address did not need to belong to a conventional mailbox that I could access separately; the application itself provided a way to view the message.

After verification, I was able to access Mattermost and join the internal team.

## 3. Enumerating Mattermost

After gaining access to Mattermost, I explored the internal channels for information that could help with further access.

One of the messages posted by `root` in the developers' channel contained two important clues:

![MatterMost 1](/assets/images/delivery_mattermost_1.png)

The message disclosed SSH credentials:

```
Username: maildeliverer
Password: <REDACTED>
```

It also hinted that users might choose passwords derived from `PleaseSubscribe!`.

The first clue provided a direct route to the target system. The second suggested a potential password-cracking strategy for later in the attack.

## 4. Initial Foothold via SSH

Using the credentials obtained from Mattermost, I connected to the target over SSH.

```
ssh maildeliverer@10.129.8.154
```

After successfully authenticating, I began enumerating the host for application files, configuration files, and other credentials.

During enumeration, I discovered the Mattermost installation under `/opt/mattermost`.

## 5. Extracting Mattermost Database Credentials

Mattermost's configuration file contained the database connection settings:

```
cat /opt/mattermost/config/config.json
```

The relevant configuration was:

```
"SqlSettings": {
    "DriverName": "mysql",
    "DataSource": "mmuser:<REDACTED>@tcp(127.0.0.1:3306)/mattermost?charset=utf8mb4,utf8&readTimeout=30s&writeTimeout=30s"
}
```

This revealed the database credentials:

```
Username: mmuser
Password: <REDACTED>
Database: mattermost
```

Since the database was listening on localhost, I could access it from my existing SSH session.

```
mysql -u mmuser -p
```

After entering the password, I listed the available databases and connected to Mattermost.

```
SHOW DATABASES;
USE mattermost;
SHOW TABLES;
```

The `Users` table was particularly interesting because it contained account information and password hashes.

```
SELECT Username, Password, Email, Roles
FROM Users;
```

The results included a `root` account with the role `system_admin system_user` and a bcrypt password hash.

At this point, I had obtained the hash but not the plaintext password.

## 6. Cracking the Mattermost Root Password

The developers' channel had explicitly mentioned password reuse and variations of:

```
PleaseSubscribe!
```

Instead of starting with a large, generic password dictionary, I used this information to build a targeted wordlist.

### 6.1 Generating password candidates

First, I created a file containing the base password.

```
echo 'PleaseSubscribe!' > password.list
```

I then applied Hashcat's `best66.rule` to generate variations of the phrase.

```
hashcat -r /usr/share/hashcat/rules/best66.rule \
  password.list --stdout > guess_password.list
```

Rule-based mutations can produce candidates involving capitalization changes, appended numbers, and other common modifications. This approach is useful when an application explicitly hints at a password pattern.

### 6.2 Extracting and cracking the hash

From the database results, I extracted the hash belonging to the Mattermost `root` account and saved it in `hash.txt`.

The hash used the bcrypt format, identified by the `$2a$` prefix and cost factor `10`. Hashcat supports this format with mode `3200`.

I ran:

```
hashcat -m 3200 hash.txt \
  --wordlist ./guess_password.list
```

Hashcat successfully recovered the password

This confirmed that the channel message was not merely general security advice; it was a practical hint toward the password used by the Mattermost administrator.


## 7. Privilege Escalation to Root

With the recovered password, I attempted to switch from `maildeliverer` to the local Linux `root` account.

```
su root
```

The authentication succeeded, confirming that the password had been reused for the system's root account.

I then retrieved the root flag:

```
cd /root
cat root.txt
```

**Root obtained.**

## 8. Attack Chain Summary

The complete attack chain was:

1. **Enumeration:** Identified SSH, nginx, and Mattermost.
    
2. **Email verification bypass through application chaining:** Used osTicket's ticket-thread functionality to retrieve a Mattermost verification link.
    
3. **Application access:** Registered and verified a Mattermost account.
    
4. **Credential disclosure:** Found SSH credentials and a password-pattern hint in an internal channel.
    
5. **Initial foothold:** Logged in as `maildeliverer` over SSH.
    
6. **Configuration enumeration:** Extracted the Mattermost database credentials from `config.json`.
    
7. **Database access:** Retrieved the `root` user's bcrypt password hash.
    
8. **Targeted cracking:** Used a custom wordlist and Hashcat rules to recover `PleaseSubscribe!21`.
    
9. **Privilege escalation:** Reused the recovered password with `su root`.
    
10. **Objective:** Read `/root/root.txt`.
